# 聚合详细设计模板

仅在 `design_baseline.status=published`、任务全部来源同时满足
`check_status=pass`、`checked_revision=source_revision`、`checked_hash=content_hash`，
且来源决策已批准并获得限域写入授权时使用。只允许完整任务范围。

```markdown
# {任务标题} · 详细设计

文档状态：草稿-阻塞 / 待评审 / 已批准 / 要求修改 / 已过期  
task_id：{task_id}  
覆盖范围：全部已发布设计  
生成时间：{yyyyMMdd HH:mm:ss}  
artifact_revision：{revision}  
hash_version：design-sha256-v1  
artifact_hash：{sha256}  
source_set_hash：{sha256}  
当前工作流状态以：[00-需求概览.md](./00-需求概览.md) 为准

> **怎么读这份文档**：第 1 章判断做什么、不做什么；第 2 章看系统怎么拆；第 3 章看关键链路怎么跑；第 4 章按功能看“问题 → 思路 → 改哪里 → 怎么跑”；接口、数据和配置总表在第 5 章；安全监控、实施顺序、风险和验收在第 6～9 章。来源与文件指纹在第 11 章，普通评审可以跳过。
>
> 本文是给人评审和实施使用的完整任务级设计。无需打开来源设计即可理解正文；本文不得创造未批准契约。批准本文不等于授权实施。

### 0.2 权威性与变更规则

- 来源设计是长期基线，本文是本任务完整实施入口，当前阶段只以 `00-需求概览.md` 为准。

- 本文变化后重新计算指纹并重新评审；设计批准与实施授权相互独立。

## 4. 功能设计

每个 workstream 对应一个功能章节，标题使用“做成后的能力/结果”，不要直接使用内部 workstream id。

### 4.X {功能结果}

推荐按以下阅读顺序组织，但不要为凑目录生成空壳小节：

1. **问题与目标**：现在有什么问题，改完达到什么效果。
2. **设计思路与边界**：为什么这样做，哪些行为保持不变。
3. **改动落点**：

   | 模块 | 类/组件/资源 | 改动 | 职责 |
   |---|---|---|---|

4. **怎么运行**：主路径、分支、失败路径、状态变化；复杂链路使用 Mermaid。
5. **关键契约**：只写本功能需要理解的接口、字段、状态、配置、错误、幂等、并发、权限和兼容规则。
6. **验收与回滚**：给出可验证结果、回滚动作和停止条件。

安全、可观测、配置、数据或迁移确实不适用时，用一句“无/不适用 + 原因”说明，不单独生成空表。
```

约束：

- 不得用链接替代实施相关正文。
- 不适用项写明“无/不适用 + 原因”。
- 允许去重和统一术语，不允许遗漏契约。
- 第 1～10 章面向人审与实施，第 11 章承载来源、覆盖与指纹审计；不得让治理话术淹没正文。
- 正文优先使用业务结果、改动位置和流程语言；内部章节引用只用于导航，不得形成“到处跳转才能看懂”的阅读路径。
- 每个 workstream 的必填内容是覆盖要求，不是固定 13 小节；允许合并表达，但不得遗漏。
- 不得用局部 workstream 生成任务级待评审/已批准状态。
- `design_required` 缺失按 true 处理；workstream 覆盖不完整时不得进入待评审。
- `aggregation-gap` 在本 Skill 内重编；`source-gap/source-conflict` 才修改来源并重新自检。
- 来源变化时本文过期；本文变化时清空 `reviewed_hash` 并重新评审。
- 人工批准前必须重算 `artifact_hash/source_set_hash`，并写入匹配的 reviewed hash。
- `changes-requested` 仅接受 `change_target=source|aggregation`；缺失或非法值按 fail-closed 停止。
- 不得把实现映射或代码现状当成新需求写进人审问题。
