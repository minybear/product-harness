# 领域调研契约

供 `analyze-requirement`（P0）与 `design-solution`（P1）共用。命中领域关键词或用户明确要求“先调研”时执行；无命中不强制。

本文件只定义触发、查阅顺序、摘要格式和门控；不维护百科正文。

## 1. 触发

从用户原始需求、`task_card`、已确认事实和相关文档中识别关键词（大小写不敏感；含常见别名）。

### 1.1 触发来源

- 用户明确要求调研。
- 需求包含尚未确认的领域术语、协议、业务状态、数据模型或外部接口。
- 项目适配器或现有文档明确列出的调研触发条件。

不维护特定行业的默认产品词表。示例：文件导入格式、身份认证协议、消息投递语义。

### 1.2 优先查阅路径（只读）

按顺序尽量取证，能本地查到的不问用户：

1. 任务内已有 `01` 证据索引、方案评估、正式设计中的领域摘要
2. 项目文档：`docs/**`、相关 `design/{模块}/`、外部服务商/接口说明
3. 代码与配置：`git_repo` 内相关协议/外部系统客户端实现与配置样例（具体模块/服务由项目自身结构决定，不写死服务名）
4. 权威规范（仅在本地/已授权来源可得时）：相关协议的官方文档或规范章节号
5. 仍不足：标为 `unknown`，写入待确认/开放问题，**不得编造协议细节**

## 2. 调研摘要格式（必填字段）

每个命中词或紧密相关词簇产出一条短摘要（默认总共不超过 8 条）：

```markdown
### {术语}

- 是什么：{一句话}
- 与本需求关系：{为何出现 / 影响哪段流程}
- 关键约束：{协议行为、状态、错误、时序、鉴权、重试、计费相关约束中与本需求有关的项}
- 常见坑：{与现网实现相关的易错点；无则省略}
- 证据：
  - source: {路径或规范章节}
    summary: {已读到的事实}
    confidence: confirmed | inferred | unknown
```

规则：

- `confirmed`：有可复核的文档/代码/规范依据
- `inferred`：合理推断，必须写明推断点，不得当作已确认契约
- `unknown`：缺证据；阻塞关键结论时必须进入待确认问题
- 禁止把 `inferred/unknown` 写成“已确认事实”或直接升格为正式设计契约

## 3. P0：需求分析门控（analyze-requirement）

1. 进入访谈或写 `01` 前，先做关键词扫描。
2. 命中则先完成调研摘要，再问用户业务取舍；能查到的协议事实不问用户。
3. 写 `01` 时：
   - 必出章仍是背景与目标、范围、验收标准
   - **只要发生过领域调研，就必须追加「证据索引」**，放入上述摘要或回链
4. 结束门控额外检查：存在 `confidence=unknown` 且会阻塞范围/验收/关键接口理解时，不得进入 `ready-for-confirmation` / 需求确认，应继续查证或把缺口列为阻塞待确认问题。
5. 无关键词命中：跳过本契约，不增加空章节。

## 4. P1：方案与正式设计门控（design-solution）

触发加深调研（在 P0 基础上）当且仅当：

- 方案或正式设计涉及协议/数据模型/业务对象接口、编解码、绑定、路由、错误码映射；或
- 变更外部连接行为；或
- `01` 中领域摘要为 `inferred/unknown`，但设计需要把它变成契约

执行：

1. **先复用** `01` 证据索引中的领域摘要，不重复从零科普。
2. 对将写入方案推荐或正式设计的条款，把相关项提升到 `confirmed`（补证据）或明确标为开放问题/不纳入范围。
3. 正式设计发布前：协议字段、状态机、错误语义、重试/幂等、安全鉴权不得只有 `inferred` 来源；否则 `waiting-user` 或回 `analyze-requirement` 补证据。
4. 在 `02-方案评估.md` 或正式设计的“依据/证据”处引用同一摘要，保持术语一致。

## 5. 停止条件

- 无命中关键词 → 不调研
- 本地与已授权来源仍无法确认，且该点阻塞范围/验收/契约 → 停止推进确认或发布，向用户列出最少问题
- 用户明确“先不调研、按假设继续” → 允许继续，但必须在风险/假设中记录，且不得把假设写成 confirmed 契约
