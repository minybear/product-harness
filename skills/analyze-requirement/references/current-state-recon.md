# 现状与依赖勘察契约

供 `analyze-requirement` 在分轮追问前执行（P0，所有需求强制）。目标：先摸清项目现状与本次需求的依赖关系，禁止只基于需求表面描述提问。

本契约只定义触发、查阅顺序、依赖清单、交互面判定与「现状与依赖基线」输出格式。项目专属事实（模块名、页面路径、配置命名空间、外部系统清单）由产品适配器或项目局部规则提供，不写死在本文件。

## 1. 触发

- 所有需求在进入分轮追问前都必须执行，无例外。
- 默认「轻量勘察」；跨模块、R3/R4、或契约/数据/接口变更时「加深」。

## 2. 输入

- 原始需求与 `task_card`。
- 产品适配器：`docs_root`（文档根）、`git_repo`（代码仓）、`owns[]/does_not_own[]`（归属边界）、`product_touchpoints[]`（涉及产品/模块）。
- 项目自身模块边界规则（若存在，如 `CLAUDE.md` / `AGENTS.md` / `.claude/rules/`）。

## 3. 勘察步骤（只读，通用查阅顺序）

1. 定位受影响面：由 `owns[]/does_not_own[]`、`product_touchpoints[]` 与项目模块边界规则定位触及的模块/服务与代码落点。未登记产品或所有权冲突记为缺口，放入访谈 frontier，不得自行补全。
2. 读现状：按顺序取证，能本地查到的不问用户——
   a. 项目文档：`docs_root` 下的设计/架构/现状文档、任务档案既有结论；
   b. 代码：`git_repo` 内相关模块的实现入口、数据模型、关键逻辑；
   c. 配置：该项目运行配置（键/命名空间/开关/阈值/模板），形态由技术栈决定；
   d. 接口：对内/对外 API、RPC、事件、外部系统对接；
   e. 外部系统：本需求涉及或依赖的外部服务/系统。
   每个事实区分 `confirmed / inferred / unknown`；`unknown` 且阻塞范围/验收时不得进入需求确认。
3. 梳依赖清单：列出需求依赖的现有能力（模块/代码/配置/数据/接口/外部系统），以及改动会波及的下游。
4. 判前后端交互面：是否有前端/UI 层；涉及配置时是否需要在前端开放配置入口（具体页面/路径由该项目适配器或局部规则提供）。判不了 → 放入 `open_questions`。
5. 产出「现状与依赖基线」（见 §5），作为 frontier 输入。

## 4. 轻量 vs 加深

| 强度 | 何时 | 覆盖 |
|---|---|---|
| 轻量 | 所有需求默认 | 定位受影响面 + 依赖清单 + 前后端交互面 |
| 加深 | 跨模块、R3/R4、契约/数据/接口变更 | 轻量之上再读具体代码实现、配置项、DTO/接口承载面、外部系统契约 |

## 5. 「现状与依赖基线」输出格式

```markdown
### 现状与依赖基线

- 受影响面：{模块/服务/代码落点}
- 现状：{现有实现是什么 / 是否已有实现 / 与本需求关系}
- 依赖清单：
  - 依赖现有能力：{模块/代码/配置/数据/接口/外部系统}
  - 波及下游：{改动的下游影响}
- 前后端交互面：{是否前端/UI；配置是否需要前端入口及归属}
- 证据：
  - source: {路径}
    summary: {事实}
    confidence: confirmed | inferred | unknown
```

## 6. 落盘

- 「现状与依赖基线」作为 `01-需求分析.md` 的必填「现状与依赖」小节落盘，并保留证据索引（见 `requirement-analysis-template.md`）。
- `inferred/unknown` 不得写成已确认事实；阻塞项进入 `open_questions` 或访谈 frontier。

## 7. 通用性约束

- 不写死任何项目的模块名、页面路径、配置命名空间、外部系统清单。
- 项目专属事实来源：产品适配器（`docs_root`/`git_repo`/`owns[]`/`touchpoints[]`）与该项目局部规则（`CLAUDE.md`/`AGENTS.md`/rules）。
- 换项目只换适配器，本契约正文不变。
