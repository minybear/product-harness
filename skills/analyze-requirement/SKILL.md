# 需求分析（analyze-requirement）

把真实需求讲清楚，为方案设计和开发授权做准备。本 skill 不做方案设计，不修改业务代码。

本项目需求阶段的权威人工确认产物是任务档案中的 `01-需求分析.md`。不创建独立 `PRD` Skill，也不把 `docs/PRD.md` 作为本流程门控产物。信息完整度评估、现状与依赖勘察、分轮问询、场景澄清、领域调研均在本 Skill 内完成，不拆成多个 Skill。

## 触发

- `ai-collab-start` 判断需要建立任务档案或进入真实需求分析。
- 用户要求“分析需求 / 梳理需求 / 明天要按真实需求跑 / 进入真实需求验证”。
- 进入开发前缺少范围、规则、验收标准或待确认问题。

## 准入

- 必须已有 `task_card`，或先用 `ai-collab-start` 生成。
- `task_card` 必须有唯一主 `product` 和 `product_touchpoints[]`；加载全部已登记适配器。所有权冲突、未登记产品或当前需求依赖 `missing_evidence` 时，将缺口放入访谈 frontier，不得自行补全。
- 若要写文件，必须确认允许创建或更新归档文档。
- 若已有任务档案，必须复用；不能因跨日新建目录。
- 续作读取快照后，只有 `next.skill=analyze-requirement` 或活跃访谈硬门控要求本 Skill 时才可执行；其他 `next.skill` 必须退回 `ai-collab-start` 按快照路由，不得因用户动作词重新做需求分析。
- 不允许在本 skill 中修改业务代码、运行测试、调用外部接口、操作数据库或部署。

## 工作步骤

1. 读取版本 INDEX、任务 INDEX、用户原始需求、`task_card` 和已有任务档案的 `00-需求概览.md`；再按需读取相关业务文档，不默认加载完整 trace。
2. **现状与依赖勘察（P0，所有需求强制）**：追问前先摸清项目现状与本次需求的依赖关系，禁止只基于需求表面描述提问。读取 `references/current-state-recon.md`：
   - 定位受影响面：用产品适配器的 `owns[]/does_not_own[]`、`product_touchpoints[]` 与项目自身模块边界规则定位触及的模块/代码落点；`git_repo` 指向代码仓、`docs_root` 指向文档根。
   - 读现状：按通用查阅顺序（项目文档/设计/现状 → 代码 → 配置 → 接口 → 外部系统）摸清现有实现、是否已有实现、与本需求的关系；能查到的问不问用户。
   - 梳依赖：列出需求依赖的现有能力（模块/代码/配置/数据/接口/外部系统）与改动会波及的下游。
   - 判交互面：是否有前端/UI 层、配置是否需要前端入口（通用表达；具体页面/路径由该项目适配器或局部规则提供）。
   - 产出「现状与依赖基线」作为 frontier 输入。默认轻量（定位 + 依赖清单 + 交互面）；跨模块、R3/R4 或契约变更时加深（读具体代码/配置/DTO 承载面）。
   - **未产出基线前不得向用户提出实现策略**（校验强度、兼容/破坏性、Header/鉴权怎么改、确认后实施）。第一轮面向用户的输出应是勘察摘要；问题只问勘察后仍无法从代码/文档得出的范围、验收或授权。
3. **领域调研（P0，命中领域词才触发）**：读取 `references/domain-research.md`，对原始需求与上下文做关键词扫描，作为现状勘察在领域侧的加深。命中 领域协议或外部服务 等协议/外部系统词或用户要求“先调研”时：
   - 先按查阅路径只读取证并写出调研摘要（是什么 / 与需求关系 / 关键约束 / 常见坑 / 证据与 confidence）
   - 能查到的协议与现网事实不问用户；`unknown` 且阻塞范围或验收时不得进入需求确认
   - 无命中则跳过，不增加空章节
4. **产品适配器门控**：核对主产品的 `docs_root/git_repo/execution_status`，合并主产品与全部 touchpoint 的 `owns[]/does_not_own[]/risk_triggers[]`。`blocked-in-this-repo` 可继续需求分析，但必须记录正确实施仓；`catalog-only` 或当前动作依赖 incomplete 字段时保持 `waiting-user`。
5. 将需求拆成“需求决策树”，并按模板输出：`01` **必须先写**背景与目标、现状与依赖、范围、验收标准；角色/场景、业务规则、数据、接口、非功能、待确认、风险等仅在有必要时追加，禁止为空章占位。做过现状勘察后**必须追加证据索引**。
6. **配置与前端入口门控**：需求涉及新增或变更运行时配置（配置项/键、租户级配置、feature flag、阈值、开关、模板名等，具体形态由该项目技术栈决定）时，必须判定是否需要**该项目的前端/门户**开放配置入口：
   - 先查该项目是否已有同类配置页/表单/命名空间；能复用则优先扩展，不默认新建菜单。
   - 需入口：业务/运维人员会改、需审计、需表单校验或需按租户/环境分域编辑 → 在 `01` 写清入口归属、配置键、字段含义、默认值来源、权限与验收（改完能在前端保存并在服务生效）。
   - 不需入口：纯研发/集成模板、随发版资源、仅 CI/运维手推且用户不会自助改 → 在 `01` 写明仅运维手推及理由，避免方案阶段遗漏运维路径。
   - 判不了归属或是否应暴露给用户 → 放入 `open_questions`，不得默认“只加配置就行”。具体页面路径、命名空间、权限模型由该项目适配器或局部规则提供，不写死在本通用 Skill。
7. 计算当前可问的 frontier：只问前置条件已明确、且会阻塞下一阶段的问题。
8. 每轮最多问 3 个问题，每个问题给出推荐答案，并以交互式问题卡展示；等待用户回答后再推进下一轮。
9. 能通过文档、代码或已有上下文查到的事实由 AI 自己查，不问用户；只有决策、取舍、授权和业务边界交给用户。
10. 每轮回答后读取 `references/requirement-interview.md`，重新评估结束门控：未满足为 `continue-interview`，满足为 `ready-for-confirmation` 或 `ready-to-draft`。领域 `unknown` 或产品适配器阻塞项未关闭时不得判定可结束。
11. 只有 `ready-to-draft` 才能输出需求分析草案、创建/更新任务档案；其他状态只继续访谈或继续调研。
12. 需要输出结构化草案或写 `01-需求分析.md` 时，读取 `references/requirement-analysis-template.md`。
13. 若用户授权落盘，写入或更新当前任务档案的 `01-需求分析.md`，并标明它是本任务人工确认的需求基线。
14. `01` 落盘后进入需求确认：默认 `waiting-user`，请用户确认范围、优先级与验收口径；仅当用户已明确“进入方案 / 确认需求分析 / 按 01 进入方案”时，才把 `next.skill` 设为 `design-solution`。
15. 阶段结束前按 `../write-plan/references/stage-handoff.md` 生成唯一下一 Skill；有落盘授权时先更新 `00-需求概览.md` 和任务 INDEX，再追加 `06-AI作业追溯.md`。

## 输出约束

- 先在内部维护 `requirement_interview` 状态；默认向用户展示可读的追问卡，不直接展示 YAML、`frontier`、`blocked_until_answered` 或长路径。
- 用户可直接自然语言回答，也可按 `Q1：...；Q2：...` 回复；不得声称已提供点击按钮、下拉框或其他宿主 UI 控件。
- 用户明确要求“导出 YAML / 原始访谈状态 / 供工具消费 / 写入结构化文件”时，才输出 fenced YAML。
- `continue-interview` 与 `ready-for-confirmation` 是硬门控：不得创建目录、任务档案、需求分析或方案文档，也不得转方案、决策卡或实施；`Qn` 回答不得被当作文件操作授权。已有任务档案仅可追加访谈摘要 trace。
- 领域调研摘要中 `inferred/unknown` 不得写成已确认事实；无证据不得编造协议细节。
- 现状与依赖勘察是强制步骤：未产出「现状与依赖」基线前不得进入分轮追问；基线必须写入 `01`（见 `references/requirement-analysis-template.md`），`inferred/unknown` 不得写成已确认事实。
- 不输出完整源码、长日志或重复上下文。
- 未授权落盘时，只给草案和下一步，不创建文件。
- 不得新建或要求独立 PRD Skill / `docs/PRD.md` 作为本项目需求阶段门控。
- 阶段结束时默认展示“当前进度”：已完成阶段、唯一下一动作、阻塞项和需要用户做的事；`next.skill` 非 `none` 时不得写成任务完成。
- 输出字段和 `01-需求分析.md` 结构见 `references/requirement-analysis-template.md`。
- 需求尚未聊清楚时，不要假装完成分析；按 `references/requirement-interview.md` 输出下一轮交互式问题卡。
- 任务 INDEX 只提供定位、当前动作和文档链接；需求事实与当前阶段以 `00-需求概览.md` 为准，访谈历史按需从 trace 恢复。

## 转交

- `01` 已落盘且用户已确认范围/优先级，或用户已明确“进入方案”：快照转 `design-solution`。R3/R4 的决策卡由方案阶段继续处理，不跳过方案设计。
- `01` 已落盘但用户尚未确认：保持 `waiting-user`，下一动作是确认需求分析；不以“已写 01”自动进入方案。
- 高风险或仍有关键决策，快照中明确为 `waiting-user` 或 `make-decision-card`，不以泛化的“待确认”结束。
- 发现暂不处理问题，转 `write-issue`。
