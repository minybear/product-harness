# 写 AI 作业追溯（trace）

trace 记录 AI 基于什么输入工作、做了什么、产生了什么结果，以及哪些风险、假设、人工确认和后续问题需要冷启动恢复。

## 归档位置

```text
docs/{项目}/tasks/{createdDate}-{模块}-{需求名}/06-AI作业追溯.md
```

同一任务跨工作日只追加新事件，不能按当天日期新建任务目录。旧 `docs/{项目}/plan/{task}/06-AI作业追溯.md` 只兼容读取，迁移后以 `tasks/` 为准。

## 什么时候必须写 trace

以下情况必须追加：需求范围/方案/验收/风险讨论、生成或更新任何结果文档、代码/配置/测试变更、命令或检查、关键判断、issue/阻塞、人工确认、跨工作日续作，以及需求/方案评估/决策/正式设计发布/实施/验证/归档之间的交接。

低风险一次性问答可以不写；一旦产生文件、命令、测试、issue 或跨轮需求，必须写。

## 定位已有任务档案

1. 用户显式提供的 task 路径、旧 plan 路径、目录名或 `task_id`。
2. 当前会话刚创建或刚引用的任务目录。
3. `docs/{项目}/INDEX.md` 中当前任务链接。
4. `docs/{项目}/tasks/README.md` 和任务 `INDEX.md` 中进行中/未完成任务。
5. `docs/{项目}/tasks/*/00-需求概览.md` 的标题、模块、关键词。
6. 旧 `plan/README.md` 与 `plan/*/00-需求概览.md`（只读兼容）。

- 唯一匹配：追加该任务的 trace。
- 多个候选：询问用户确认。
- 没有 task 但已产生文件/命令/测试/issue：先走 `write-plan` 建立或关联任务档案。
- 活跃访谈且没有任务档案：不得为写 trace 触发建档；在会话中保留摘要，待 `ready-to-draft` 后一次性归档。

## trace entry 格式

```markdown
## TRACE-{yyyyMMdd-HHmmss}-{短标题}

- 时间：
- 阶段：需求接入 / 需求分析 / 方案评估 / 决策 / 正式设计发布 / 开发 / 测试 / 文档 / 归档 / 问题登记
- 原始输入：
- 结构化任务卡：
- AI 返问记录：
- 用户补充内容：
- AI 执行动作：
- 文件变更：
- 命令执行结果：
- 测试结果：
- 风险与假设：
- 人工审核记录：
- 阶段交接：完成阶段 / 当前状态 / 下一 Skill / 下一动作 / 正式设计基线 / 阻塞项 / 用户动作
- 交付物路径：
- 新增/关联 issue：
- 下一步：
```

## 记录粒度与关系

按有意义的工作单元记录，不要为每一次读取文件单独建事件。命令记录关键结论；失败记录失败原因和后续处理。

- `write-plan`：创建或维护任务档案并初始化 trace。
- `write-ai-trace`：追加过程事件。
- `write-issue`：登记待处理问题并回写 issue 链接。
- `write-worklog`：汇总阶段完成结果并链接 trace。

## 关键要求

- trace 归属任务，不归属日期。
- 阶段交接必须与 `00-需求概览.md` 的快照一致；trace 是历史，不替代当前状态源。
- 落盘后若只追加 trace、不更新 `00`/INDEX，该 trace 不得当作阶段已推进；续作仍以 `00` 为准，并须先补快照。
- 快照推进绑定工作完成，不绑定 git commit。人代提交时，AI 当轮仍须更新 `00`；提交后只把 commit 证据写入后续 trace。
- trace 不是当前状态源，也不是冷启动时的默认全文上下文；阶段迁移先更新 `00-需求概览.md` 和任务 INDEX，再追加一条摘要事件。
- 恢复任务时默认读取 INDEX、`00-需求概览.md` 和相关交付物；只有需要审计、追问恢复或核对依据时才读取 trace 片段。
- 结果文档、代码变更、命令、测试、风险、审核和 issue 都必须可追溯。
